# electron-three-windows

Упрощённая версия Electron-приложения. При запуске открывает одно окно с тремя независимыми веб-панелями одинаковой ширины.

## Настройка ссылок

Адреса задаются в полях `url` массива `panels` файла `config.json`. Пустой адрес показывает пустую панель. При первом запуске шаблон конфигурации копируется в системную папку данных пользователя; после сохранения рабочего файла приложение автоматически обновляет панели.

Если при запуске одна или несколько панелей не настроены, приложение автоматически открывает окно первоначальной настройки и просит указать три HTTP/HTTPS-адреса.

Чтобы изменить адреса позднее, выберите пункт «Настройки панелей…» в системном меню или нажмите `Ctrl+,` на Windows/Linux либо `⌘,` на macOS. После сохранения панели обновятся без перезапуска.

## Архитектура

Предметная модель отделена от Electron: `Panel` и `PanelAddress` управляют состоянием панели, `PanelCollection` гарантирует состав, а `EqualPanelLayout` рассчитывает равные области. Работа с конфигурацией, окном и `WebContentsView` вынесена в отдельные классы инфраструктуры.

## Запуск

```sh
bun install
bun start
```

Проверка контрактов TypeScript:

```sh
bun run typecheck
```

Проверка кода:

```sh
bun run lint
```

## Сборка

```sh
bun run build:win
bun run build:mac
bun run build:linux
```

Готовые установщики сохраняются в папке `dist`.

### macOS: сообщение «приложение повреждено»

Текущая macOS-сборка не подписана сертификатом **Developer ID** и не нотарифицирована Apple. Поэтому Gatekeeper может показать сообщение «Панель управления is damaged and can’t be opened» для DMG, скачанного из браузера. Это сообщение не обязательно означает, что файл действительно повреждён.

Для разового запуска собственной доверенной сборки:

1. Откройте DMG и перенесите приложение в папку `/Applications`.
2. Закройте DMG.
3. Выполните в Terminal:

```sh
xattr -dr com.apple.quarantine "/Applications/Панель управления.app"
```

4. Запустите приложение повторно.

Удаляйте атрибут quarantine только у сборки, полученной из доверенного источника. Эта команда отключает одну из проверок безопасности macOS для выбранного приложения.

Для публичного распространения без ручной команды необходимо:

1. Зарегистрироваться в Apple Developer Program.
2. Получить сертификат **Developer ID Application**.
3. Добавить сертификат и данные нотарификации в GitHub Actions Secrets, не сохраняя их в репозитории.
4. Настроить workflow на подписание, Hardened Runtime и нотарификацию macOS-сборки.

Требования описаны в документации [Apple](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) и [electron-builder](https://www.electron.build/v26/docs/mac/).

## GitHub Actions

При push и pull request workflow **Линтинг и тесты** запускает только автоматические тесты и ESLint. Компиляция TypeScript входит в команду тестов. Релизные задачи при этих событиях не создаются и не отображаются как пропущенные.

Публикация формы GitHub Release отдельно запускает workflow **Сборка релиза** для выбранного тега. После успешных тестов и линтинга `.exe`, `.dmg` и `.AppImage` автоматически прикрепляются к постоянному релизу. Временные артефакты GitHub Actions удаляются после переноса файлов.

## Релизный цикл

### Плавающий релиз latest

После каждого успешного workflow **Линтинг и тесты** для нового коммита в `main` автоматически запускается **Обновление latest**:

1. Собираются приложения для Windows x64, macOS ARM64 и Linux x64.
2. Тег `latest` переносится на проверенный коммит.
3. Создаётся либо обновляется релиз **Последняя сборка main**.
4. Старые `.exe`, `.dmg` и `.AppImage` заменяются новыми файлами.
5. Временные артефакты GitHub Actions удаляются.

Файлы плавающего релиза имеют постоянные имена без номера SemVer и дефисов: `ControlPanel_latest_x64.exe`, `ControlPanel_latest_arm64.dmg` и `ControlPanel_latest_x64.AppImage`.

`latest` намеренно отмечается как последний релиз GitHub и отображается выше стабильных версий. Это постоянно обновляемая сборка текущего состояния `main`, поэтому для воспроизводимого развёртывания следует выбирать стабильный тег `vX.Y.Z`.

Для работы плавающего релиза функция [**Immutable releases**](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) должна быть выключена: тег `latest` перемещается, а файлы релиза заменяются при каждом обновлении.

### Стабильный релиз vX.Y.Z

Раздел **Releases** используется для постоянной публикации готовых версий приложения. Релиз привязан к тегу, содержит описание изменений и установочные файлы для пользователей.

1. Убедитесь, что нужный коммит находится в GitHub и проверки для него проходят.
2. На главной странице репозитория откройте **Releases → Create a new release**.
3. В поле **Choose a tag** создайте SemVer-тег с обязательным префиксом `v`, например `v1.2.4`, и выберите коммит или ветку, которую нужно собрать. Если коммит уже имеет подходящий тег, выберите существующий — повторно создавать его не нужно.
4. Выбирайте номер версии по правилам SemVer:
   - `patch` — исправления без новых возможностей, например `v1.2.3 → v1.2.4`;
   - `minor` — новые обратно совместимые возможности, например `v1.2.3 → v1.3.0`;
   - `major` — несовместимые изменения, например `v1.2.3 → v2.0.0`.
5. Укажите название, например `Панель управления v1.2.4`, и нажмите **Generate release notes** либо напишите список изменений самостоятельно.
6. При необходимости отметьте релиз как предварительный. Прикреплять установщики вручную не нужно.
7. Нажмите **Publish release**. Публикация запустит workflow, который проверит тег, соберёт приложения и добавит установщики в этот релиз. Файлы появятся через несколько минут.
8. Откройте вкладку **Actions**, убедитесь, что запуск **Сборка релиза** завершился успешно, затем проверьте файлы на странице релиза.

Черновик релиза не запускает сборку до нажатия **Publish release**. Если в репозитории включены неизменяемые релизы, после публикации заменить установщики нельзя — сначала убедитесь, что сборка нужного тега проходит успешно.

Существующие теги и опубликованные релизы автоматически повторно не собираются. Сборку запускает только публикация нового релиза через форму GitHub Releases.

Подробная инструкция: [управление релизами в документации GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository?tool=webui).

Локальный запуск тестов: `bun run test`.
